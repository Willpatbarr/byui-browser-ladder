Ladder Test Site

A public site of byui-browser test pages, one per complexity level. A level is done when the browser shows a big SUCCESS on that level's page.

│Need

The byui-browser project is built by several student teams working in parallel. There is no shared, objective definition of when the browser, or any one feature, is "done".

GapEffect
No agreed finish line per featureTeams judge their own completeness, and those judgements don't line up
No common test targetIntegration problems surface late, when teams' pieces first meet
Heavy test suites (such as WPT) need a working JavaScript engineAn early-stage browser can't be measured at all

│Solution

A public website of test pages, the Ladder, organised into eight levels of increasing complexity (L0–L7). Each level adds exactly one capability. A team opens a level's URL in the browser: a large SUCCESS means the level passes.

RequirementHow the Ladder meets it
Objective pass/failFrom L2 up, pages show FAIL by default; only the feature under test can reveal SUCCESS
Usable from day oneL0 and L1 need nothing beyond text and basic HTML
Zero setupStatic pages on GitHub Pages; no harness, server or install
Clear next stepThe first failing level names the next feature to build
Defined finish lineThe browser is complete when every level passes

Live at willpatbarr.github.io/byui-browser-ladder.

│The idea in one screen

Problem

Teams have no shared definition of when a browser feature is "done".

Mechanism

One web page per level. The page tests a single feature and shows SUCCESS only if that feature works.

Pass

A big SUCCESS on the page. No tools, logs or test harness needed: just open the URL.

Done

The browser is complete when L0 through L7 all pass.

│The ladder

Each level adds exactly one capability on top of the level before it, so the first level that fails shows which feature to work on next.

LevelTestsPage
L0Plain text, no tags/l0/
L1Static HTML with default styling: headings, paragraphs, lists, links/l1/
L2Inline CSS and <style> blocks/l2/
L3External resources: linked stylesheet, image, web font/l3/
L4Interaction: link navigation, form submit, back/forward/l4/
L5JavaScript that changes the DOM/l5/
L6Network and timers: fetch, setTimeout/l6/
L7Real-world sites, linked out/l7/

The root page is L1-level HTML only, with no CSS or JavaScript, so any browser that passes L1 can use it to reach every level.

│Success rule

A page may use only its own level's feature to show SUCCESS. Pages from L2 up start out showing FAIL, and the feature under test is the only thing that can hide it.

Browser stateL0–L1 showsL2+ shows
Feature worksSUCCESSSUCCESS
Feature missingnothing readable (page fails to render)FAIL
Feature half-workspartly readableFAIL
RememberThe rule's one guarantee: a browser without the feature sees FAIL, never a false SUCCESS. Each page also says in plain text what it tests and what a pass looks like.

│How each level reveals SUCCESS

LevelDefaultWhat switches it to SUCCESS
L0SUCCESSThe page is just the word, as plain text
L1SUCCESSAn <h1>; passes if it renders
L2FAILA <style> rule hides FAIL; ::before writes SUCCESS
L3FAILThe same trick, but only in the linked style.css; the image also spells SUCCESS
L4FAILFollowing the link or submitting the form lands on a SUCCESS page
L5FAILA script replaces the heading text
L6FAILOne heading filled from a fetched result.json, one from a timer
L7noneChecked by hand: each linked site loads and its links work

Example: the L2 mechanism

CSS hides FAIL and writes SUCCESS; with no CSS, FAIL stays

html
<style>
.fail { display: none; }
.result::before { content: "SUCCESS"; }
</style>
...
<h1 class="result"><span class="fail">FAIL</span></h1>

│Constraints

Plain static pages can't check everything. Where a page can't prove a pass by itself, it tells the tester what to look for.

L3 web font

No CSS-only way to show FAIL when a font doesn't load. The page says what the font should look like (a curly script).

L4 back/forward

History can't be checked without JavaScript, which belongs to L5. The tester presses Back and Forward and checks where they land.

L7 real sites

There's no automatic SUCCESS on real sites. Passing is a judgement call.

L0 file type

GitHub Pages serves L0 as HTML, so the page contains no tags and reads the same either way.

ObservationHosting is static only: no build step, no backend. Anything that needs a server, such as recording which teams passed, is future work.

│Future work

The first version keeps the rule minimal on purpose. Planned additions:

  1. A separate pass/fail line for each check within a level, not one verdict per page
  2. console.log success output, once the browser has developer tools
  3. Pass reports sent to a server or dashboard, so passes are recorded
  4. Email sign-up for updates (items 3 and 4 both need a backend)
  5. More levels as the browser grows, such as layout, accessibility and media
